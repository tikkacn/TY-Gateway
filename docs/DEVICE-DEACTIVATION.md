# 管理员设备反激活

入口：管理员后台 → 设备中心 → 查看详情 → **设备反激活**。输入该设备 MAC，再确认执行。不是用户侧功能。

反激活用于设备重新刷机、重新建立注册身份；不要用它修复普通分流问题。

| 操作 | 注册身份 | 用户分流 | MAC 准入 / FRP |
| --- | --- | --- | --- |
| 禁用设备 | 保留记录，可再启用 | 保留 | 保留登记，拒绝服务 |
| 重置客户分流 | 保留 | 清除客户自定义偏好，回到基础规则 | 不变 |
| 反激活设备 | 撤销旧凭据，移出设备中心 | 清除该设备全部云端规则、偏好及命令 | 保留 MAC 及当前方案/订阅预绑定/备注，恢复待激活 30 天；释放旧 FRP 登记 |

反激活不擦除物理设备系统、本地密码、本地配置或缓存策略，不是远程恢复出厂，也不是离线设备的即时断网控制。正在运行的旧 Agent 不会凭旧身份自动重新认领；普通升级/重跑安装器保留本机凭据，也不会自动绕过反激活。用户重新刷系统再一键安装，会生成新密钥并认领保留的 MAC。旧机器身份与旧待注册密钥均不能再次使用。

新设备会获得新的设备 ID、顺延编号；单台反激活不重排其他设备。若要整个测试环境从 1 编号，属于另一个需要明确授权的整体清理操作。共享订阅源、规则库、其他设备和审计历史不删除。

FRP 云端登记在事务提交时释放。授权插件每分钟同步一次名单；名单更新后旧 Login、Ping、工作/用户连接等均被拒绝，原生 OIDC 不再为旧身份签发 token。实际隧道停止受名单同步和心跳影响；云端不可达时撤销可能延迟，不能把按钮成功当作实时断链证明。新身份分配端口前检查现有监听，跳过尚被旧连接占用的端口，并保留数据库唯一约束。

## 部署顺序与实现

先备份 TY 数据库，再应用 `migrations/008_device_deactivation.sql`，然后更新 Cloud。设备端不需要新软件包；与 v0.8.6 Agent 兼容。

`POST /api/v1/admin/devices/deactivate` 需要管理员认证；Cookie 会话要求同源。请求包含设备 ID、预期配置版本、确认 MAC 和 `DEACTIVATE_DEVICE`。版本或 MAC 不匹配直接拒绝；旧页面不能误删同 MAC 的新身份。

数据库事务同时写旧密钥哈希黑名单、审计事件、重置 MAC 认领并删除设备记录；任何步骤失败全部回滚。删除通过现有外键级联清除设备规则、偏好和命令。黑名单只存哈希，不存凭据明文；不可随意清空，否则旧待注册请求可能重放。迁移缺失时认领失败关闭，不悄悄跳过黑名单。

## 本轮验收范围

针对性检查：MAC/版本/确认和同源保护、并发重复请求、旧身份/旧密钥拒绝、保留当前基础策略和订阅、FRP 名单撤销、占用端口避让、其他设备不受影响、界面小按钮及确认流程。

另有只在 `ty_deactivation_test_` 前缀隔离库执行的 SQL 检查：迁移可重跑、外键级联删除、订阅预留、审计事件，以及故意让审计写入失败后整笔操作回滚。正式设备记录不用于这项测试。

实机待用户配合：在测试设备反激活后检查 SSH 入口最终断开；重新刷机并通过 GitHub 一键安装，确认新身份、自动 FRP 和订阅下发恢复。不会为软件检查反激活真实设备。
